### 1. Set AI credit session limits in Copilot CLI and SDK

- 출처: GitHub Changelog
- 날짜: 2026-07-01
- URL: https://github.blog/changelog/2026-07-01-set-ai-credit-session-limits-in-copilot-cli-and-sdk/
- 왜 중요한가: GitHub Copilot CLI와 SDK에서 session 단위 AI credit soft cap을 설정할 수 있게 되었다. 특히 사람이 지켜보지 않는 자동화 실행에서 비용 폭주를 막는 제어 장치다.
- 한국어 요약: 에이전트 자동화는 "성공할 때까지 계속 실행"되면 비용과 시간의 상한이 흐려진다. GitHub는 `--max-ai-credits`와 `/limits`로 model calls, subagents, background compaction까지 포함한 세션 사용량을 추적하고 한도 도달 시 종료 또는 조정을 요구한다. 이는 에이전트를 cron, CI, 백그라운드 작업에 넣기 위한 운영 기본값에 가깝다.
- 구체적 takeaway: 이 vault 자동화도 장기적으로 "리서치 개수", "웹 요청 수", "토큰/비용 한도", "중복 항목 제외"를 명시한 실행 예산을 갖는 편이 좋다.

### 2. Harness engineering for coding agent users

- 출처: Martin Fowler / Thoughtworks
- 날짜: 2026-04-02
- URL: https://martinfowler.com/articles/harness-engineering.html
- 왜 중요한가: 코딩 에이전트 신뢰도를 높이는 방법을 모델 교체가 아니라 guide와 sensor로 이루어진 외부 하네스 설계 문제로 설명한다.
- 한국어 요약: 글은 에이전트에게 좋은 결과를 기대하려면 두 방향의 장치가 필요하다고 본다. 먼저 feedforward controls는 규칙, 참고 문서, 코드베이스 맥락처럼 에이전트가 행동하기 전에 방향을 잡아준다. feedback controls는 테스트, linter, static analysis, logs, browser 관찰처럼 행동 후 결과를 검증하고 self-correction을 유도한다. 핵심은 "사람이 리뷰한다"를 마지막 방어선으로 두지 않고, agent가 스스로 고칠 수 있는 신호를 시스템 안에 넣는 것이다.
- 구체적 takeaway: 프로젝트마다 AGENTS.md, lint/test 명령, architecture rule, domain glossary를 한 묶음으로 관리하면 에이전트 품질 편차를 줄일 수 있다.

### 3. The VibeSec Reckoning

- 출처: Martin Fowler / Thoughtworks
- 날짜: 2026-05-27
- URL: https://martinfowler.com/articles/vibesec-reckoning.html
- 왜 중요한가: AI-assisted 개발과 citizen builder 흐름에서 prompt로 "secure하게 해줘"라고 말하는 것만으로는 부족하다는 실제 near-miss 사례를 다룬다.
- 한국어 요약: AI가 public storage, 과도한 service account 권한처럼 "가장 쉬운 경로"를 제안할 수 있다는 점이 핵심이다. 글은 보안 context file, permission 질문 습관, daily security intelligence feed, secure-by-default template을 제안한다. 특히 보안 규칙은 prompt가 아니라 versioned context와 CI gate, SAST, secret scan, IaC validation으로 강제되어야 한다.
- 구체적 takeaway: AI로 만든 인프라/백엔드 코드는 PR 전에 최소한 secret scan, dependency audit, IAM 권한 diff, public access check를 통과해야 한다.

### 4. Best practices for developing and deploying cloud infrastructure with the AWS CDK

- 출처: AWS CDK Developer Guide
- 날짜: 2026-07-02 관측
- URL: https://docs.aws.amazon.com/cdk/v2/guide/best-practices.html
- 왜 중요한가: CDK 앱을 애플리케이션, 런타임 코드, 구성, 인프라가 함께 리뷰되고 테스트되는 배포 단위로 다루는 공식 best practices다.
- 한국어 요약: AWS는 CDK가 CloudFormation template을 쓰기 편하게 만드는 도구가 아니라, 전체 애플리케이션 상태를 코드로 묶어 리뷰, 테스트, 롤백 가능하게 만드는 모델이라고 설명한다. 조직 차원에서는 landing zone과 CI/CD 계정을 분리하고, 개발팀은 별도 계정에서 테스트하며, production stage는 코드로 모델링하는 흐름이 권장된다. 또한 stateful resource의 logical ID 변경, hardcoded physical name, synthesis 중 network lookup 같은 실수를 경계한다.
- 구체적 takeaway: 인프라 정리 작업은 "리소스 목록 문서화"보다 CDK construct 경계, stack 배포 단위, logical ID 안정성 테스트부터 잡는 편이 안전하다.

### 5. Top announcements of the AWS Summit in New York, 2026

- 출처: AWS News Blog
- 날짜: 2026-06-17
- URL: https://aws.amazon.com/blogs/aws/top-announcements-of-the-aws-summit-in-new-york-2026/
- 왜 중요한가: Bedrock AgentCore, AWS Context, AWS Continuum, AWS Security Agent 등 AWS가 agentic AI를 운영, 보안, 데이터 거버넌스 층으로 끌어올리는 방향을 보여준다.
- 한국어 요약: AWS의 메시지는 agent를 단순 챗봇 기능으로 보지 않고, 조직 데이터 관계를 runtime knowledge graph로 제공하고, 보안 취약점 우선순위와 remediation 흐름까지 연결하는 플랫폼 기능으로 다루는 것이다. 특히 Continuum과 Security Agent는 threat modeling, STRIDE 기반 mitigation, PR code scanning, IDE/MCP 통합을 언급한다. AI 에이전트가 강해질수록 보안 검토와 수정 작업도 에이전트 작업면에 붙는 흐름이다.
- 구체적 takeaway: AWS 기반 AI 기능을 설계할 때는 Bedrock 호출 코드보다 먼저 data governance, threat model, remediation workflow, audit trail을 아키텍처에 포함해야 한다.
